肌肉分离效果和可复用方案是硬门槛：
- 必须严格复刻参考图中独立肌群的分离、层级、曲线、阴影/高光、斜向肌纤维纹理、描边和前后视构图。生产渲染和验收截图中严禁用简单多边形、矩形、椭圆、占位块、均匀色块或默认图标替代人体轮廓和肌肉 mask；这类占位实现不得标记为完成，也不能作为“视觉近似”交付。
- 优先检索并评估可嵌入的 Flutter 包、开源 SVG/Rive/Canvas 资产和 GitHub 项目，再决定是否自研。阶段 0 和阶段 2 开始前必须记录候选的 URL、固定版本/提交、SDK 兼容性、维护状态、代码许可证、内置艺术资产许可证、署名要求、是否允许修改/商用/再分发，以及与参考图的视觉差距。
- 候选只有在路径级肌肉分离、前后视覆盖、热度/纹理可扩展、命中测试和许可证都可接受，并且截图对比证明能达到目标时，才优先通过 adapter 接入。代码许可证不等于艺术资产许可证；`NOASSERTION`、只有前视、需要付费资产、无法确认资产来源或无法达到参考图分离效果的方案不得直接纳入生产依赖。
- 当前可优先核验的候选包括：`flutter_body_heatmap`（nyandrianinamamy/flutter_body_heap_map，MIT，纯 Flutter、前/后视、23 个区域和连续热度）；`flutter_muscle_anatomy`（angujo/flutter_muscle_anatomy，BSD-3-Clause，前/后视 SVG 与 Path 访问）；`muscle_mapper`（suryamolly/muscle_mapper，MIT，细粒度 SVG、BYOA、命中测试与热度）；`flutter_body_atlas`（kit-g/flutter-body-atlas，BSD-3-Clause 代码，内置图需单独 CC BY 4.0 署名）；`bodychart_heatmap`（Obaloluwa-Obidoyin/bodychart_heatmap，MIT，较粗粒度热力图）；`muscle_map`（SquashVash/muscle-map，MIT，前/后视选择和强度图）。`rive_muscle_heatmap` 的 Dart 代码为 MIT，但免费 `.riv` 资产是前视 18 肌群，后视/强度/点击能力依赖另行授权的付费资产，不能假设满足本项目目标。候选版本必须以 `docs/reusable_projects_research.md` 和执行时的 pub.dev/GitHub 复核为准。
- 如果没有候选同时满足视觉、技术和许可证要求，才进入自研；自研必须使用逐肌群的高保真 SVG 路径或等价曲线/Path 数据，并保留来源、绘制工具、许可证和测量证据。不得为了赶进度退回简单多边形。

目标技术栈和边界：
- Flutter SDK + Dart。
- Riverpod 2 负责状态和依赖注入；UI 不直接写持久化细节。
- Hive（或当前 Flutter SDK 兼容的 Hive 变体）保存训练记录、动作模板、组数、重量、训练日志和身体数据；SharedPreferences 只保存主题、单位、默认模板等简单设置。
- Freezed + json_serializable 负责不可变数据模型、复制和 JSON 备份序列化；生成文件必须加入构建流程。
- Cupertino 组件与 Material 3 混用，整体保持克制的 iOS 风格；flutter_animate 负责明确的入场、切换和反馈动画；gap 统一间距；fl_chart 用于力量和体重趋势。
- permission_handler、flutter_local_notifications、path_provider、share_plus、csv/json 按需接入。通知、导出和权限都必须有失败和取消分支，不能阻塞核心记录。
- dio、cached_network_image、AI API 和传感器属于可选扩展，默认关闭且不能成为核心流程依赖；默认数据必须可离线使用。

必须覆盖的产品能力：
1. 动作库和训练模板：动作名称、目标肌群、器械/分类、模板顺序、目标组数和目标次数。
2. 训练记录：开始/结束时间、动作、组、次数、重量、RPE/备注（可选）、完成状态和编辑/删除。
3. 训练历史和统计：按日期、动作和肌群查询，展示总训练量、PR/趋势和体重变化；空状态、错误状态和无数据状态要可用。
4. 身体数据：体重等可扩展测量项，单位设置和输入校验。
5. 导出与备份：JSON 必须可往返解析；CSV 可读；分享失败、取消和无权限时给出可理解反馈。
6. 提醒：训练提醒和通知权限请求可选；拒绝权限仍然可以记录训练。
7. 肌肉热力图：前视和后视两个人体图、肌群高亮、选择状态、训练量映射、标签/引线和响应式布局。

肌肉热力图是最高优先级的视觉模块，按以下要求实现：
- 视觉目标是参考图中的深色圆角面板、左右前/后人体轮廓、深蓝灰基础解剖分区、橙/红/黄色热度渐变、肌纤维斜向纹理、清晰深色描边、英文字母或本地化标签、细引线和白色端点；具体颜色、间距、比例和文字位置应从参考图测量并记录为 token，而不是凭感觉重画。
- 使用可维护的 SVG/Canvas/CustomPainter 图层或等价矢量方案。人体轮廓、肌群区域、热度叠加、纹理、标签和命中测试要分层，不能把整张位图当作唯一的交互层，也不能把参考图直接当作最终产品资源来伪装完成实现。
- 定义稳定的肌群 ID 和前/后视映射，至少覆盖胸、三角肌、斜方肌、背阔肌、腹肌、肱二头肌、肱三头肌、臀肌、股四头肌、腘绳肌和小腿；显示名应支持本地化，数据 ID 不随文案改变。
- 热度值必须由训练记录聚合得到，并定义归一化、无数据、极值、对称肌群和日期范围规则。颜色图例、选择状态和无数据状态必须可理解。
- 支持前/后视切换、点击肌群查看训练摘要、日期范围筛选、无障碍语义标签和不同屏幕宽度下的稳定缩放；标签不能遮挡人体或彼此重叠。
- 为热力图建立视觉回归截图或等价的可重复证据。目标尺寸至少覆盖一个常见 Android 窄屏和一个较宽屏幕；若无法做像素差异，要记录人工比对方法、已知偏差和未验证项。

建议架构：
- 按 feature 划分 `features/workout`、`features/exercises`、`features/body_metrics`、`features/heatmap`、`features/settings`、`features/export` 等；共享模型、主题和存储接口放在 `core`。
- Repository 负责 Hive/SharedPreferences 和序列化，Notifier/Provider 负责 Riverpod 状态，Widget 负责渲染和用户事件。不要在 build 方法里做数据库写入或重量级聚合。
- 记录 schema 需考虑版本号、迁移和备份兼容；时间统一存储，展示时根据设备设置格式化。
- 交互、动画、错误、加载、空状态和表单校验都要有测试或可复现检查。

## 主 Goal 的完成定义

新对话中的 Codex 必须把 Goal 当作持续任务：先检查，随后按阶段实施、验证和修复。单独输出一份计划不算完成；没有运行结果、截图或明确未验证项的“已完成”也不算完成。
