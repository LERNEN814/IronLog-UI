## 4. 偏离规格 / 自行解释之处
1. **`WeightUnit` 提前到 T1.1 创建**：`UnitConverter` 签名需要该类型，T1.3 未重复创建（PROGRESS Q1）。
2. **Git 提交身份**：本机全局无 Git 身份，设置了仅本仓库的 `IronLog Coder <coder@ironlog.local>`，与 M0 的 `IronLog Auditor` 区分（PROGRESS Q2）。
3. **表数量**：任务卡写"8 张表"，实际按 DATA_MODEL §3 实现 **7 张 SQLite 表**；`user_settings` 按 §3.8 是 DataStore Preferences，不是表（PROGRESS Q3）。
4. **`summarize` 增加 `nowMillis` 参数**：§4 要求进行中会话用 `Clock.nowMillis()`，但红线 5 禁止在 `core/time` 外取时间，因此由调用方注入；签名变为 4 参（PROGRESS Q4）。
5. **`exerciseCount` / `bodyRegions` 口径**：规格未定义。`exerciseCount` = 至少 1 个已完成组（不限组类型）的条目数；`bodyRegions` = 会话全部条目对应动作的 PRIMARY 肌群 `body_region` 集合（PROGRESS Q5）。
6. **`PrefillPlanner.plan(lastSets, kind)` 的 `kind` 参数在本里程碑未参与分支**：P1–P4 的行为与 kind 无关，保留参数以符合签名，后续若有"有氧/力量占位组差异"再使用。
7. **`observeRecentSessions` 只返回 FINISHED 会话**：进行中会话由 `observeInProgressSession` 单独提供，避免主页"继续训练"与"最近训练"重复。
8. **`session_exercise.exercise_id` 加了 FK → `exercise.id` 及索引**：DATA_MODEL §3.5 标注了该 FK；任务卡只显式要求两个 CASCADE FK 的索引。

## 5. 已知问题 / 技术债
1. **`startSession()` 非并发安全**：仅靠"先查后插"保证唯一 IN_PROGRESS；SQLite 无法在不改 schema 的情况下加部分唯一索引。M1–M2 均为单线程 UI 调用，风险低；若 M3 引入并行调用，应在 schema v2 迁移中加 `CREATE UNIQUE INDEX ... WHERE status = 0`。
2. **`upsertCustom` 未使用事务**：exercise 行与 exercise_muscle 映射的多次写入之间崩溃会丢失映射。M1 无编辑界面；M2 做自定义动作编辑器时用 `RoomDatabase.withTransaction` 包裹。
3. **`SettingsDataStore` 无单元测试**：DataStore 文件 I/O 测试留到有设置界面（M6）时补。
4. **种子动作 66 个**：满足 M1 ≥60；M2 结束前需补到 ≥100（DATA_MODEL §5）。
5. **`ExerciseDao.search` 的 `kindFilter` 是 `Int?`（枚举 ordinal）**：M2 的 UI/ViewModel 需做 `ExerciseKind` 转换。
6. **`SessionSummary` 的 `durationS` 可能为负**：若系统时钟回拨且会话进行中，未做 clamp（规格未要求）。
