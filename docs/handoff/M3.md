## 4. 偏离规格 / 自行解释之处
1. **T3.2 与 T3.3 合并为一个提交**（`7fef340`）：`RestAlarmReceiver` → `RestTimerRepository` → `RestAlarmScheduler` 形成类型环，拆开会导致中间提交无法编译；T3.5 的边界测试仍单独提交（`ba830c8`）。
2. **恢复时把剩余时间当作 total**：数据库只有 `rest_target_at`，不新增列（schema v1 冻结），因此进度环从满开始重走；规格未要求保留原始总时长。
3. **`finish()` 无计时时是 no-op**（`e93c690`）：避免在无计时状态下调用 `AlarmManager.cancel`；`skip()` 复用 `finish()`。
4. **精确/非精确分支的验证方式**：Robolectric 的 `ScheduledAlarm` 不暴露 exact 标志，测试用 `schedule()` 返回值（false 即走了 inexact 分支）+ `ELAPSED_REALTIME_WAKEUP` + `allowWhileIdle` 断言；这是 shadow 能给出的最强证据。
5. **冷进程闹钟由 §7.1（D5）覆盖**：无内存计时时读 `rest_target_at`，过期 → 提醒并清空，未来 → 恢复；旧版“直接 return 丢提醒”的行为已作废。
6. **训练页单位切换不持久化、距离按设置单位、时长 D4 口径**（T3.0，M2 审计已批准）。
7. **去掉了 `RestTimerRepository` 构造时的自动 `restore()`**：恢复只由 `MainActivity.onStart` / `SessionViewModel.init` 触发——否则冷进程闹钟到来前，init 的 restore 会先把过期目标静默清掉（TR4/TR5 测试相应改为显式调用 `restore()`）。
8. **通知点击导航在 MainActivity 实现**（冷启动读 `intent`，运行中走 `onNewIntent` + `launchMode=singleTop`），由 `IronLogNavHost(openSessionId=…)` 消费；导航行为本身无自动化测试。

## 5. 已知问题 / 技术债
1. **UI 层无自动化测试**：计时条渲染、Sheet 交互、提示音/震动、权限对话框仅靠编译 + `@Preview` + 真机验收。
2. **应用内提示音在勿扰/静音下无声**：遵循系统设置（规格要求）；震动 300ms 仍会执行。
3. **`ProcessForegroundState` 依赖 `ProcessLifecycleOwner`**，只能在真机/Robolectric 环境构造；单元测试用 `FakeForegroundState`。
4. **`RestTimerBar` 的每秒刷新由 UI `LaunchedEffect` 驱动**（ViewModel `refreshRestTimer()`），ViewModel 内没有常驻 ticker；息屏后 UI 不刷新（后台由通知 Chronometer 负责）。
5. **连续完成两组会关闭当前计时并重开选择器**：符合“重新 start 覆盖旧计时”的规格，但没有二次确认。
6. **M2 的 6 项真机验收仍未填写**（见下），M2 审计要求“M3 交接前必须补齐”。
7. **`RestAlarmReceiver.onReceive` 的 Android 胶水无自动化测试**（`goAsync` → Hilt 字段注入 → `onAlarmFired` → `pendingResult.finish`，以及 PendingIntent 的实际投递）；冷进程业务逻辑已由 TR6/TR6b/TR7 + TR8 覆盖，这一段留真机验证。
