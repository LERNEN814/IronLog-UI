# AUDIT — 里程碑审计协议

> 流程：**编码代理自证 → 审计官裁定 → 下一步指令**。
> 审计官（项目发起人 + 我）保留最终裁定权。`scripts/verify.sh` 的输出是"最低门槛"，不是"通过证明"。

---

## 第 1 步：让编码代理产出审计包

里程碑交接报告写完后，把下面这段发给编码代理：

```
=== 审计包提示词开始 ===
审计官开始审计 M<n>。请**只做取证，不要修改任何代码**，输出以下内容。

1. `git log --oneline m<n-1>-audited..HEAD`（首次审计用 `m0-baseline..HEAD`）的完整输出。
2. `bash scripts/verify.sh` 的完整输出（最后 40 行），以及 `bash scripts/verify.sh --quick` 的输出。
3. 对 `docs/tasks/M<n>.md` 中的每一个任务，列出：
   - 该任务的验收命令，以及它的实际执行结果（贴关键输出，不要只说"通过"）。
   - 涉及的源文件清单（相对路径）。
   - 对应的测试类与测试方法数量（用 `grep -c "@Test"` 统计，给出具体数字）。
4. 检查自己是否触碰了红线，逐条回答（R1–R12）：
   - 是否修改过任何受保护文件？（若是，列出文件与 diff 摘要）
   - 是否有任何 `@Ignore`、被删除的断言、被放宽的断言、被吞掉的异常？
   - 是否有 `docs/tasks/M<n>.md` 要求之外的额外功能？列出文件与用途。
   - 是否新增了依赖？（列出坐标与版本）
   - 数据库 `version` 是否发生过变化？（列出 schema 目录下的所有文件）
   - 是否有任何测试是"为了让测试通过而改实现"的？如实说明。
5. 逐条对照 `docs/DOMAIN_RULES.md` 中属于本里程碑的测试向量表：给出"规格条数 / 已实现条数 / 测试类名"。**有不一致的地方必须指出**。
6. 列出你认为**最可能出问题**的 3 个地方（自评），以及你没有验证到的假设。
7. 列出所有"偏离规格"和"自行解释"之处。

要求：如实、具体、可核对。不要美化。审计官会独立复算数值、独立运行命令。
=== 审计包提示词结束 ===
```

## 第 2 步：审计官执行清单

### 2.1 通用检查（每个里程碑都做）

| # | 检查 | 方法 |
|---|------|------|
| G1 | 提交粒度：每个任务 ≥ 1 个提交，消息格式 `M<n>-T<k>: ...` | `git log --format="%h %s" m<n-1>-audited..HEAD` |
| G2 | 门禁真实通过 | 自己跑一次 `bash scripts/verify.sh`（不要相信代理的输出） |
| G3 | 受保护文件零改动 | `git diff --stat m<n-1>-audited..HEAD -- <PROTECTED 列表>` 应为空；`python scripts/check_rules.py` 应 0 fail |
| G4 | 无灌水测试 | 抽查测试文件：断言是否真的断言了行为（而不是 `assertTrue(true)`）；`grep -rn "assertThat" app/src/test \| wc -l` 与测试数量的比例是否合理 |
| G5 | 无"伪造通过" | `git diff m<n-1>-audited..HEAD -- app/src/main \| grep -n "^\-"`，搜索被删掉的 `assert`、被改宽的条件 |
| G6 | 领域逻辑无 android 依赖 | `grep -rn "^import android" app/src/main/java/com/ironlog/app/domain/` 应为空 |
| G7 | 时间来源唯一 | `grep -rn "System.currentTimeMillis\|LocalDate.now()" app/src/main --include=*.kt` 只允许命中 `core/time/` |
| G8 | 数值独立复算 | 见 2.3：审计官用自己的参考实现重算至少 5 个向量 |
| G9 | 测试零跳过 | 检查 `app/build/test-results/testDebugUnitTest/*.xml` 中 `skipped="0"` |
| G10 | 交接报告真实性 | 报告中的每个声明都要能在代码/命令输出里找到依据 |

### 2.2 各里程碑专项

**M1**
- 数据库 v1 `schema JSON` 的字段与 `docs/DATA_MODEL.md` 逐列比对（列名、类型、可空、默认值、外键、索引）。**这是最关键的检查**——v1 冻结后再改要付迁移成本。
- `unit` 相关：枚举是否叫 `WeightUnit`（不是 `Unit`）；枚举 ordinal 顺序与文档一致。
- `UnitConverter`：**独立复算 U1–U22 中的至少 6 条**（用 Python/手算），特别是 U6–U10 的 lb 往返。
- `FatigueModel`：独立复算 F1、F4、F7、F10、F12（跨半衰期、多会话叠加、边界窗口、时钟回拨）。
- `getLastSetsForExercise` 的 SQL：检查是否真的实现了"跳过无已完成组的条目"（R2 用例必须是真数据驱动，不能是 mock）。
- 种子数据：`exercise` 条数 ≥ 60；每个动作的 `primary_muscle_id` 在 muscles 中存在；主动肌 role=PRIMARY 且 weight=1.0。
- 红线 R6 抽查：`workout_set` 表中是否出现过 Real 列。

**M2**
- 交互符合 `docs/PRD.md` R-2.x 逐条对照；尤其 R-2.4（占位值语义）、R-2.5（热身组不参与序号）、R-2.10（全部未完成时的丢弃确认）。
- "每次交互立即落库"：检查 ViewModel 是否在同一函数里先写库再更新 UI，而不是只在结束时批量写。
- ViewModel 是否直接依赖 DAO（应通过 domain 接口）。
- `@Preview` 是否存在且用假数据。

**M3**（最高风险）
- `AlarmRestAlarmScheduler` 的权限分支（`setExactAndAllowWhileIdle` vs `setAndAllowWhileIdle`）是否有测试覆盖。
- 是否有任何前台服务、`setAlarmClock`、被禁权限（R10）。
- 进程恢复逻辑：`restore()` 的三个分支（空 / 未来 / 已过期）是否都有测试。
- 用户真机验收结果是否真的填了（不能是代理自己编的"通过"）。
- 通知渠道的重要性级别是否符合 REST_TIMER §6。

**M4**
- 日历网格的边界（闰年、月首/月末补空）是否有真测试。
- 编辑历史训练后，汇总数字是否重算（而不是缓存）。
- "以模板开始训练"是否用的是预填规则而不是照抄旧组值。

**M5**
- 热力图：`FatigueRepository` 的查询窗口与 `FatigueModel` 的窗口是否一致（不能重复过滤或漏过滤）。
- 分享图：位图尺寸、MediaStore 写入、FileProvider 配置是否齐备。
- PR 判定是否严格大于（相等不算）。

**M6**
- 导入失败时**数据未被清空**（这是数据安全的关键路径，必须有测试）。
- 往返一致性：导出 → 导入 → 逐表条数与内容一致。
- `assembleRelease` + R8 后在真机上跑通主流程。

### 2.3 数值独立复算（审计官用参考实现，不引用代理代码）

审计官保有一份独立的参考实现（Python），用于复算：
- 单位换算：`grams = round_half_up(value × 453.59237)`（lb）/ `value × 1000`（kg）
- 疲劳度：`fatigue = Σ stimulus × weight × 0.5^(age_h / half_life)`
- 1RM：`weight × (1 + reps / 30)`
- 汇总：`Σ weight_g × reps`

复算结果与代码行为不一致 → 判定为 **不通过**。

## 第 3 步：审计结论与下一步指令

### 3.1 判定等级

| 等级 | 条件 | 处理 |
|------|------|------|
| **通过** | 门禁 0 FAIL；专项检查无实质问题；数值复算一致 | 打 tag `m<n>-audited`，发下一步指令 |
| **有条件通过** | 门禁通过，但有 ≤ 3 处不影响后续里程碑的问题（如命名不规范、缺 `@Preview`、注释错误） | 打 tag，把问题写进下一步指令的"顺手修"列表 |
| **不通过** | 门禁 FAIL；或红线违规；或数值复算不一致；或交付物与任务卡不符 | **不打 tag**，列出必须修复的清单，要求修复后重新提交审计包 |

### 3.2 审计记录

每次审计写一份 `docs/audit/M<n>.md`（审计官写，代理不得修改）：

```markdown
# M<n> 审计记录 — <日期>

**结论**：通过 / 有条件通过 / 不通过
**基线**：<起始 sha> .. <结束 sha>，tag: m<n>-audited（若通过）

## 门禁
- scripts/verify.sh：<自跑结果>
- 受保护文件：<无改动 / 列表>

## 检查结果
| 检查项 | 结果 | 证据 |
|-------|------|------|

## 数值复算
| 向量 | 规格 | 代码结果 | 审计官复算 | 一致? |

## 必须修复（不通过时）
1.

## 顺手修（下一里程碑内处理）
1.

## 设计变更决定
（例如：批准某项 schema 变更、批准新增依赖、调整规格）
```

### 3.3 下一步指令格式

审计结束后，发给代理的指令必须包含：

```markdown
## M<n> 审计结论：<通过/有条件通过/不通过>

## 下一步：M<n+1>
1. 打开 docs/tasks/M<n+1>.md，这次的任务是 T<k>..T<m>。
2. 顺手修（合并到相关任务的提交里，不要单独开一堆提交）：
   - ...
3. 设计变更（已批准）：
   - ...
4. 保持不变的红线：见 AGENTS.md §5。
5. 完成标准同前：`bash scripts/verify.sh` = 0 FAIL + docs/handoff/M<n+1>.md。
6. 完成后停止并报告，不要开始再下一个里程碑。
```

### 3.4 审计官自己不做的三件事
1. 不直接改代理的代码（发现问题 → 写进指令让它改，保持"谁写的谁修"）。
2. 不修改自己写下的规格去迎合实现（规格错了要走"设计变更决定"流程并留痕）。
3. 不在门禁 FAIL 的情况下打 tag——tag 是"这个版本可回退"的承诺。
